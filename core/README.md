# 🧠 @notification-platform/core

**Ядро доменной области (Shared Kernel)** платформы уведомлений. Единый источник истины для типов, интерфейсов и контрактов, обеспечивающий строгую типизацию и согласованность данных между микросервисами (`receive-service`, `delivery-service`).

---

## 🚀 Основные возможности

- **Shared Kernel (DDD)**: Централизованное хранение доменных моделей (`Notification`, `Contact`, `Initiator`) и перечислений (`ChannelType`, `StrategyType`), исключающее дублирование определений.
- **Compile-time Safety**: Гарантия целостности контрактов. Изменения в структуре данных автоматически подсвечиваются компилятором во всех зависимых сервисах.
- **Zero Runtime**: Пакет содержит только декларации типов и интерфейсов. Отсутствие логики выполнения, побочных эффектов и внешних зависимостей гарантирует минимальный размер и мгновенную загрузку.

---

## 🛠 Использование

Пакет предназначен исключительно для импорта типов и интерфейсов в бизнес-логике сервисов. Не содержит исполняемого кода.

```typescript
// Импорт доменных сущностей и типов
import {
  type Notification,
  type ChannelType,
  CHANNEL_TYPE,
} from "@notification-platform/core";

// Использование в интерфейсах функций
const sendNotification = async (
  notification: Notification,
  channel: ChannelType,
): Promise<void> => {
  if (channel === CHANNEL_TYPE.EMAIL) {
    // Логика отправки email
  }
};
```

## 🔒 Принципы и Требования

Для сохранения чистоты ядра и предотвращения циклических зависимостей необходимо строго соблюдать следующие правила при разработке внутри этого пакета:

1.  **Zero Dependencies**: Запрещено добавлять любые внешние `dependencies`. Разрешены только `devDependencies` для линтинга и тестирования типов.
2.  **Zero Runtime**: Запрещено создавать классы с реализацией, синглтоны, выполнять побочные эффекты или импортировать модули, выполняющие код при загрузке. Только `type`, `interface`, `enum`, `const` (с данными).
3.  **Strict Isolation**: Логика, специфичная для конкретного сервиса (например, детали подключения к БД или специфичные мапперы), должна оставаться в сервисах, а не мигрировать в Core.
4.  **Backward Compatibility**: Любое ломающее изменение (breaking change) требует повышения мажорной версии и синхронного обновления всех зависимых сервисов.
